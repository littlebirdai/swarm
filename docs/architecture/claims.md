# Baton and terminal claims

The claims table keeps one row per resource. A server mutation reads the row through the `by_kind_resource` index. Convex serializes concurrent claims on the same key. The first successful claim issues token 1. Each subsequent claim adds 1.

## Caller contract

- Check conversation access, sender grants, terminal grants, and owner authority before you call the helper. The `CallerAuthorized` types identify this requirement. Derive the resource and holder from server state.
- Use the conversation ID for the baton and the immutable pane instance ID for terminal typing. The pane ID must distinguish each instance across machines and runs. Resolve the current pane before you check a token.
- Use `steering.mode: "lone"` when the turn implies the starter's right. On the first request from a second sender, use `mode: "second_request"` with the starter as `holder`. Queue the second sender's message in the same mutation. Use `mode: "contested"` after the caller records the transition. Presence alone does not start it.
- Use `readClaimToken` to obtain the generation for a new request. Keep the same resource, holder, request ID, and `expectedToken` when you retry. A live retry returns the existing token and the remaining time. A retry after release or expiry returns `inactive_request`. A retry after a later grant returns `stale_request`. Refresh the generation only for a new request.
- Call `checkClaim` in the same mutation as the guarded write. Proceed only if it returns `held`. Use the returned `remainingMs` for client timers. The server expires a lease when its clock reaches the deadline.
- Renew a live baton lease for 30 seconds. The design specifies renewal at half the lease when another sender can send. Terminal typing uses 20 seconds, the duration of the existing pane viewing lease. The terminal model leaves the duration open. Renewal cannot revive an expired lease.
- Revoke the specific holder and token. For a baton takeover, stop the old holder's writes first. Grant the successor after the delivery settles or the daemon acknowledges the fence. The caller owns this sequence and the terminal control protocol.

## Retention

Keep each claim row indefinitely. Release and revoke remove the holder and set the deadline to zero. Expiry leaves the row in place. Every row retains the last token and request ID. A future purge must prove the resource can never be claimed again or preserve the token in durable storage. Conversation cleanup, lease expiry, and pane restart must preserve this high-water mark.

The table stays on the server. It has no sync feed, public functions, keystrokes, or secrets. The request ID is a non-secret identifier.
